Implementation blueprint · standalone

A T3-shaped foundation with deliberate delivery lanes.

This plan defines the project shell only: engineering conventions, infrastructure, environments, observability, and change control. It intentionally contains no product flows, entities, or assumptions from a demo or specification.

System at a glance

One TypeScript application is deployed per environment. The web app and a self-hosted Convex service run together on Railway, while Clerk and PostHog remain managed integrations.

Application conventions

01

TypeScript first

Strict TypeScript, path aliases, Zod at every trust boundary, and explicit environment parsing at startup.

02

T3 sensibility

Small composable modules, server-first defaults, predictable naming, linting/formatting, and pragmatic code over framework theater.

03

shadcn/ui system

Tailwind CSS tokens plus local shadcn/ui components. Components are owned by the repository, not hidden behind a package abstraction.

04

Convex-native data

Queries, mutations, actions, schemas, authorization checks, and generated types live beside the application code. Do not add a second API layer by default.

Authentication boundary

Clerk owns sign-in and session lifecycle. The application accepts only Clerk-issued tokens, validates them in Convex using the configured JWT template, and maps identity claims to application roles/permissions. Authorization is enforced in Convex functions, never only in the UI.

Analytics boundary

PostHog is initialized after consent/session readiness. Capture a concise, documented event vocabulary; identify users with a stable non-sensitive application identifier; capture server-side operational events only where client capture is unreliable. Never send secrets or protected user content.

Railway topology

Create one Railway project with isolated development, preview, and production environments. Each environment has its own services, data stores, variables, and domains.

ServiceResponsibilityEnvironment rule
webBuilds and runs the Next.js app.One deployment per Railway environment; receives only that environment’s public URLs and keys.
convexRuns the pinned, supported self-hosted Convex runtime topology.Dedicated deployment and persistent volume/configuration per environment; never share its data plane across lanes.
postgresDurable backing database required by the self-hosted Convex deployment.Private service, separate database and credentials per environment; backups enabled for production.
object storageDurable file/blob storage used by Convex when enabled.Separate bucket/prefix and credentials per environment; lifecycle and recovery policy documented.

Pin the exact Convex self-hosted release and deploy its official supported topology. Treat upgrades as planned infrastructure changes: rehearse in development, promote through preview, back up production, then release.

  • Feature branches may never deploy directly to shared production infrastructure.

CI, secrets, and quality gates

Pull request checks

  • Install from lockfile
  • Typecheck and lint
  • Unit/integration tests
  • Production build
  • Convex schema/function validation
  • Dependency/security scan

Environment configuration

  • Store secrets in Railway/GitHub secrets, never committed files.
  • Use .env.example with names only.
  • Separate Clerk instances/keys and PostHog projects or tagged environments.
  • Validate required variables before startup.

Operational signals

  • Structured application logs with deployment SHA.
  • Railway health checks for web and Convex services.
  • PostHog release tagging and environment filtering.
  • Document alerts, backup ownership, and restore tests.

Agent and reviewer contract

RuleRequired practice
Agents do not land changesEvery agent creates a focused branch and opens a pull request. Direct pushes to dev, preview, and main are blocked.
PRs provide evidenceUse the PR template: objective, scope, tests run, deployment/environment impact, migration notes, analytics/auth impact, and rollback notes.
Independent reviewA different authorized agent or human reviews the diff and checks before approving. The author cannot approve or merge their own PR.
Protected promotionRequire passing CI, one approval, resolved conversations, current branch state, and merge queue/rebase policy before merge.
Reviewer mergesThe reviewer (or release owner) merges after approval. Promotion PRs follow the same rule, with production requiring the designated release reviewer.

AGENTS.md is the canonical in-repository instruction: it must restate these rules, name the validation commands, prohibit secret disclosure, and require a PR URL in every agent handoff.
