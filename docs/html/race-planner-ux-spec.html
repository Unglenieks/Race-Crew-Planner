UX build specification / v2.0

Make the tool adapt to the race.

This document defines the user experience Race Planner must provide across disciplines: rally, road racing, endurance, karting, track days, drag racing, off-road and club events. It specifies what people can control, what each control does, and why it earns a place in the product.

It is written to be testable. Every requirement should be provable by watching one person, on one device, in the conditions the event actually happens in.

Scope boundary This is a UX specification, not a visual design or technical architecture. A capability is only in scope if a user can perceive, configure, act on, or recover from it. Where a requirement carries a number — type size, contrast, touch target, timeout — that number is part of the user experience and is binding.

00 / revision notes

What v1.3 got wrong.

v1.3 described a flexible workspace well and then quietly assumed the important part: that information which is published is information which arrived. It also asserted usability goals — readable, touchable, glove-friendly — without a single number anyone could fail a build against. These are the corrections.

Findings from the v1.3 review
PROBLEM FOUND IN v1.3WHAT CHANGED IN v2.0WHY IT MATTERED
“Publish” was treated as the end of a change New §09 defines per-recipient delivery state, an unreached list, escalation, and verbal-acknowledgement capture. Publishing is not complete until every affected person is reached or explicitly escalated. The worst realistic failure of this product is a driver leaving service on last night’s instruction. v1.3 could be built exactly to spec and still allow it.
Usability goals had no thresholds New §12 sets binding minimums for type size, contrast, touch target, keyboard operation, announcement and latency, plus night and sunlight conditions. “Readable contrast” and “generous targets” cannot be reviewed, tested or failed. Numbers can.
The empty product was undefined New §10 covers first run, minimum event setup, every empty collection, and sample data that can be removed in one action. v1.3 promised a new team could be productive quickly but never described the screen they actually meet first.
“Failure states” meant offline only §11 now carries a failure matrix: load, permission, deleted record, stale view, publish, upload, export, storage, expired link, revoked access, no search results. Offline is one failure. A crew hits the others on the same day, usually while hurrying.
Today was the default surface but had no requirements §02 now specifies Today and the attention queue, including what may never be buried and what a user may pin. The most-used screen in the product was the least specified.
Reversibility was described as archive plus confirmation Guardrail A now splits the two: immediate undo for reversible actions, impact statement and confirmation only for irreversible ones. Confirming everything trains people to confirm without reading, which removes the protection it claims to add.
Document pointed at the wrong prototype and could not be navigated Link now resolves to the companion prototype; section list is sticky and tracks position; tables restack instead of scrolling sideways; headings scale on small screens; §14 maps every section to a screen. A specification nobody can navigate or trace is not usable by the team meant to build from it.
Honest limitation Three questions are still open and are called out in §14 rather than hidden behind confident prose: how a change reaches someone with no data at all, who owns event structure when the owner is driving, and whether cross-event reporting belongs in this product.
01 / non-negotiable experience principles

Flexibility must be progressive.

A new team should be productive with a plan, a few places and a checklist. An experienced team must be able to evolve that starting point without having to invent a separate system outside the app.

01
Start with defaults; never trap users in them.Race Planner supplies practical racing templates and types, but every type, field, status, category, view and template can be changed by an authorized user.
02
Keep the record separate from its presentation.Changing a table column, saved view or personal dashboard does not change the event’s underlying records or another person’s preferred workspace.
03
Make uncertainty visible.Draft, published, confirmed, changed, missing, unassigned and offline states must be explicit. Color may reinforce a state; it must never be the only signal, and a state may never be dropped to save space on a small screen.
04
Favor optional links over required data entry.A user can create a plain plan row, note, task or place in one action. Links to a car, person, venue, source or form are offered in context and can be added later.
05
A change is not done until it arrives.Any instruction that affects where a person goes or what a person does carries a visible delivery and acknowledgement state per recipient. The product never reports success on the sender’s side alone.
06
Design for the conditions, not the demo.Cold hands, gloves, direct sun, darkness, engine noise, one free hand, split attention and no signal are the normal operating environment. Anything that only works seated indoors on a fast connection is unfinished.
07
Prefer undo to confirmation.Reversible actions happen immediately and offer undo. Confirmation is reserved for what cannot be undone, and must state the specific impact rather than ask a generic question.
02 / workspace shell, today and attention

Every screen should answer: where am I, what needs attention, and what can I do?

Persistent shell controls
CONTROLUSER ACTION & RESULTWHY IT EXISTS
Event switcherOpens the event picker; creates, duplicates, archives or opens an event; shows date range, timezone, selected vehicle(s), sharing state and offline readiness.Teams often operate multiple events and cars. Context must be unmistakable before a user edits a plan or completes a form.
Primary navigationMoves among Today, Plan, Work, Records, Forms and Files. Users may reorder, hide or pin modules they have access to; the event owner sets the default order. When a detail screen is open, its parent module stays visibly selected.Different disciplines and roles do not work in the same sequence. Navigation should reflect the crew’s operating model, and a user three levels deep must still know where they are.
Global AddCreates a movement, work item, record, form submission, file, note or saved view. The menu remembers the user’s common choices and supports a keyboard shortcut, shown with the correct modifier for the user’s platform.Capture must stay fast when information arrives over a radio, phone call or paddock conversation.
Search / command paletteSearches names, IDs, notes and file text; also opens views and invokes actions such as “add venue” or “download Saturday.” Results show record type and event context, are keyboard-navigable, and an empty result explains what was searched and offers to create the thing instead.Users should not need to remember which module owns a fact in a live event, and a dead end must still offer a way forward.
Attention indicatorCarries a count and opens a focused queue: assigned work, plan changes needing acknowledgement, changes the user published that have not reached everyone, failed form rules, mentions, sync conflicts and expiring access. Items are dismissible only by resolution or explicit snooze with a stated return time.It prevents a generic notification stream from burying the information that can affect the day.
Sync / offline statusAlways visible, on every screen size. Shows last successful sync, queued change count, conflicts, downloaded package size and a direct route to resolve a problem.“Offline ready” is an operational condition, not decorative status text — so it cannot be the thing that gets hidden on a phone.
Draft indicatorWhen a user holds unpublished edits, the affected screen states how many and offers review. Leaving the screen or the app does not discard them or hide them.Editing without publishing is a normal, deliberate state. It must never be a state the user has forgotten they are in.
Display modeSwitches day, night and high-contrast presentation, following the device setting by default and remembering an explicit choice per device.The same crew uses this screen in a bright paddock at noon and in a dark car at 22:00. One palette cannot serve both.
Today and the attention queue
CONTROLUSER ACTION & RESULTWHY IT EXISTS
Run of dayShows what is next in event time, with place, people, status and source. Each entry opens its movement detail, and each is actionable from Today without going to Plan first.Most sessions in a live event are a ten-second check of the next commitment, not a planning session.
Summary countsDisplays counts such as movements today, work due, changes awaiting review and next handoff. Every count is a control that opens the exact filtered list behind it.A number that cannot be opened forces the user to go and rebuild the filter that produced it.
Change bannerStates what changed since the user last looked, who changed it, on whose authority, and what the user must do about it. It persists until acknowledged rather than passing by.The one thing a briefing surface exists to do is stop someone acting on superseded information.
Pinned blocksLets a user pin a filtered collection, map, latest changes or a freeform note. Pinning is personal and never alters event data or another person’s Today.A driver, crew chief and organizer liaison need different first screens from the same event.
Required rule Nothing in the attention queue may be cleared by the system on the user’s behalf. An item leaves the queue when it is resolved, explicitly snoozed with a stated return time, or no longer applies — and in the last case the queue says so rather than silently removing it.
03 / collections, views and layout

Any collection needs more than one useful surface.

A collection is a set of records such as movements, work, places or cars. Views are user-configured ways of seeing the same set. A crew may use a table during planning, a timeline during race day and a map while traveling.

View and field controls
CONTROLUSER ACTION & RESULTWHY IT EXISTS
New viewStarts a table, timeline, calendar, board, map, list or document view. The user names it, chooses private/shared/default visibility and may start from a template.Different questions require different arrangements; creating a useful view must not require spreadsheet expertise.
Fields / columnsAdds a field to the collection; chooses field type, help text, default, allowed values, validation and whether it is required. In a current view, users show, hide, reorder, resize or freeze fields.Teams need different information without making every screen unreadably dense.
Filter, sort and groupBuilds readable conditions using current fields; can save the result to the view. A visible summary states active filters and a one-click reset clears them.Saved operational slices—“my open work,” “Saturday car 262,” “unconfirmed venues”—are more valuable than one master list.
View settingsSets compact/comfortable density, grouping, visible totals, conditional highlighting, pinned summary blocks and time zone/display preferences. A user can reset only their local changes.High-density planning and quick mobile scanning are both legitimate, but must not impose on one another.
Responsive behaviour of a viewOn a narrow screen a view reflows: rows stack, secondary fields move to a second line, and the record’s state and primary action stay on screen. The user may choose which fields lead on small screens.Dropping columns to fit a phone is how a status or a primary action disappears at exactly the moment it matters. Reflow is required; truncation of state is not permitted.
Share / lock viewShares a view with roles or named people, makes it an event default, or locks its structure while still allowing permitted data edits.A race director or crew chief needs a dependable shared briefing; individuals still need freedom to experiment safely.
Bulk selectionSelects rows with mouse, keyboard or filter; supports edit, assign, tag, move, export, duplicate, archive and change status, with a review count before applying and a single undo after.Real event data arrives in batches. Repetitive one-record editing encourages errors.
Required ruleAll view configuration is reversible. The product must distinguish “this view changed” from “these records changed,” and state who will see the result before save.
04 / records, venues and categories

Let teams name their world without corrupting the event’s official facts.

Race Planner should ship with racing-aware record types, but the user—not the product—decides the vocabulary. “Venue,” “paddock,” “pit,” “service,” “fuel,” “medical,” “supplier,” “marshal post” and “hospitality” may all matter in different series.

+ Record

Add a record

Creates a person, place, vehicle, service, equipment item, organization or a user-defined type. The creator can begin with only a name, then add details and links later.

+ Type

Add or edit a record type

Names the type, chooses its icon, defaults, fields, allowed links and list behavior. Existing types can be renamed or archived; their records remain intact and discoverable.

+ Category

Group places or services

Creates a user-owned category such as Fuel, Tire support, Catering, Recovery, Charging or Media. It can be ordered, renamed, recolored and shown in a map or list view.

04b / venue-specific controls

A location is more than an address.

Place, venue and travel controls
CONTROLUSER ACTION & RESULTWHY IT EXISTS
Add venueCreates an official location from blank, a template or a map search. User selects a type or creates one, then enters address/coordinates, access notes, hours, contacts, map/directions and source.Official locations need stronger context than a generic pin, while still allowing a one-minute capture.
Add service / nearby placeCreates a crew-useful place and assigns one or more categories. A service can also be promoted to an official venue if its role changes.“Fuel near the track” and “official paddock entrance” are different truths; mixing them loses operational clarity.
Manage categoriesAdds, renames, reorders, merges, archives and colors categories; chooses whether a category appears in the left navigation, map legend or default filter. Removing a category asks whether to reassign its records.Users need their own taxonomy, but category cleanup must not silently orphan records.
Travel contextAdds a travel estimate or route note from any selected place to another. It records calculation/author/date and can be shown in plan, map or place detail.“15 minutes from paddock” is often more actionable than a street address.
Venue confirmationSets source-backed confirmation state, verification date and responsible person; can request acknowledgement from affected roles after an important change.A changed gate, paddock or inspection location needs an auditable, visible handoff—not just an edited note.
Record detail panelOpens a stable panel with properties, linked records, activity, comments, files, source excerpts and actions. Users can choose which sections are expanded by default in their view.Context belongs beside the object, not scattered across separate modules.
Offline map and directionsStates whether the map area and route for a place are downloaded, and hands off to device navigation with the access note attached rather than the bare address.The last mile of a venue change is a gate, a lot and a wrong entrance — details a map pin alone will not carry.
05 / movement plan

Planning must be as easy as a document and as dependable as a schedule.

Plan controls
CONTROLUSER ACTION & RESULTWHY IT EXISTS
Quick movement rowAdds a row with time and description; time may be exact, approximate, a range, all-day or intentionally blank. A movement becomes structured only when the user adds people, place, vehicle, status or links.Early planning is incomplete by nature. Required schema should not force fake precision.
Day / session organizerCreates, renames, reorders and groups days, sessions, legs, runs, stints or user-defined sections. Selecting one changes the records shown and the selection survives navigation away and back.Race formats vary. The product cannot assume a five-day rally or a single race day — and a day selector that does not filter is a decoration.
Publish changesLets an authorized person keep edits as draft, publish a selected change, add a reason/source and assign acknowledgement. The product highlights the delta, notifies only affected people, keeps the previous value in history, and then tracks delivery per §09.Race-day changes must be actionable without creating alert fatigue or erasing the original instruction.
Conflict / overlap helperOptionally flags overlapping commitments for the same person, car, place or resource. It never blocks a save; the user can dismiss, explain or resolve the conflict.It catches accidental double booking while respecting the realities of parallel teams and exceptions.
Plan export / printExports the selected view to printable PDF, spreadsheet, share link or compact offline brief. The preview shows the exact filter, timezone and generated time, and the printed output repeats them on the page.Some teams still need a laminated sheet or a simple handoff outside the app — and a printed sheet with no timestamp becomes a hazard the moment the plan changes.
Superseded outputWhen a plan changes after an export or share link was produced, the product marks that output as out of date wherever it can still be seen, and tells the person who created it.Paper and links outlive the change that invalidates them. The product knows; the crew should too.
06 / work, checklists and templates

Work should fit the crew’s habits, not redefine them.

Work and template controls
CONTROLUSER ACTION & RESULTWHY IT EXISTS
Create checklist / work collectionStarts blank or from a template; chooses item types, statuses, fields, view and access. A checklist can remain a plain tick list or evolve into a richer work collection.Meal prep and a multi-car service operation should not be forced into the same complexity on day one.
Task controlsSupports completion, owner, due context, status, priority, comments, attachments, linked records and custom fields. Each is optional; “complete” is always one obvious control that works with gloves and offers undo.Fast completion is critical, but richer coordination should be available when needed.
TemplatesCreates, edits, versions, copies and archives templates. When applying one, users choose destination, linked vehicle/day and whether edits are local or update the template.Teams repeat work but need to adapt it by event, car and weather without damaging the source template.
Recurrence / automationOptionally creates recurring work or rules based on a date, status or plan event. The setup screen previews the exact records that will be created or notified, and every automated record says which rule produced it.Automation should reduce routine work without surprising a crew on a busy day, or leaving them unable to find out where a task came from.
07 / forms and inspections

Flexible capture; permanent completed evidence.

Form controls
CONTROLUSER ACTION & RESULTWHY IT EXISTS
Form builderAdds, reorders, groups and configures text, number, date/time, select, multi-select, boolean, file/photo, person, signature, record link, calculated and repeatable fields. Each field has instructions, required state, defaults and validation.Inspection, inventory, incident and handoff forms share a flexible pattern but require different data.
Conditional logicShows a field, section, required state or follow-up action only when a defined answer meets a condition. The builder includes a plain-language preview of the rule.It keeps completion short while still collecting exception detail when it matters.
Submit / save draftSaves a local draft at any time, clearly marks incomplete required fields, and submits with timestamp, submitter, applicable signatures and linked records.Field users need safe interruption and must know whether a record is actually complete.
Blocked submissionIf required answers are missing, the product names how many, lists them as links, marks each field in place, moves focus to the first one, and keeps that message on screen until resolved. It never reports the block only in a message that disappears.A transient toast is the least reliable place to put the reason someone cannot finish — especially on a phone, in the dark, with one hand.
Template versioningCreates a new template version for structural edits. Completed submissions retain the version, field labels, rules and choices that existed at completion.Historical inspections cannot become ambiguous when the template evolves.
Follow-up creationLets a configured answer create or suggest a work item, plan note or escalation. The resulting record links back to the exact answer that triggered it.Finding a defect must lead cleanly to action without altering the original inspection.
08 / source, activity, permissions and recovery

Flexibility needs a memory.

Trust and recovery controls
CONTROLUSER ACTION & RESULTWHY IT EXISTS
Source attachment / excerptAttaches an original file, link, photo or quoted excerpt to a fact or change. The detail view displays source, author, date and the records that rely on it.Teams must be able to distinguish a clean operational summary from the document that justified it.
Activity & commentsShows human-readable history, comments, mentions, acknowledgements and linked changes on a record. Users can filter noise from their personal activity view, and the filters actually change what is listed.Event work is collaborative; trust requires knowing what changed and why.
PermissionsSeparates event role from product access. Owners choose who can view, comment, create, edit, publish, manage structure, submit forms and see sensitive collections.A driver, crew member, organizer contact and temporary volunteer may all need different access without different event identities.
UndoAny reversible action — completing an item, applying a filter, a bulk edit, an archive — can be undone immediately from where it happened, without hunting through history.Recovery that requires knowing the audit trail exists is not recovery for someone with cold hands and 40 seconds.
Archive / restoreArchives records, views, templates and categories with an explanation of impact. Users can restore within the retention window; destructive deletion requires explicit elevated confirmation.Configuration freedom must not permit accidental loss of an event’s operational history.
09 / change delivery and acknowledgement

Published is not the same as received.

This is the requirement v1.3 was missing. A movement plan is only worth what the crew acts on, so the product must treat reaching a person as part of the change, and must never let the publisher believe a change landed when it did not.

Delivery controls and states
CONTROLUSER ACTION & RESULTWHY IT EXISTS
Per-recipient delivery stateEach affected person carries an explicit state: not sent, sent, delivered to a device, opened, acknowledged, unreachable, or acknowledged by another route. The publisher sees the list, not a total.“8 people notified” hides the one person who never got it — which is the only fact that mattered.
Unreached listShows who has not received or acknowledged a change, with when each was last online and their next likely contact point. It stays available until the change is fully reached or deliberately closed.Closing this gap is a human task. The product’s job is to make the gap impossible to overlook.
SeverityThe publisher marks a change routine or critical. Routine changes batch; critical changes alert immediately, repeat, override quiet settings and require acknowledgement.Without severity, everything alerts, so people mute the channel and the critical change is the one they miss.
EscalationIf a critical change is unacknowledged after a chosen interval, the product notifies a named fallback — crew chief, team manager, or the whole crew — and records that it did.Someone driving, under a car or in a stage cannot answer. The plan for that must exist before it is needed.
Out-of-band acknowledgementAnyone may record that a person was reached by radio, phone or in person, naming who confirmed it and when. The record shows the change was closed this way.Most real acknowledgement happens by voice. If the product cannot record that, its delivery data becomes fiction.
Recipient view of a changeThe recipient sees what changed, the previous instruction, who authorised it, the source, what they must do, and one obvious acknowledge control. Acknowledging is one action and states what it commits them to.Acknowledgement must mean “I have read and will act,” which requires showing enough to make that true.
Offline recipientsA change queued for an offline person is stated as pending delivery to the publisher, and is presented to the recipient on reconnect as new even if it is hours old, with its original time and current validity.A change discovered late must not look like a change already handled.
Required rules
  • No change that affects location, timing, safety or scrutineering may be marked complete while any affected recipient is unreached and un-escalated.
  • The publisher’s confirmation screen reports reach, not send: “6 of 8 reached, 2 pending” — never “published successfully.”
  • Acknowledgement is always attributable to a person and a time, including when it is recorded on someone’s behalf, in which case both people are named.
  • A superseded instruction stays readable in history, marked superseded, with what replaced it.
10 / first run and empty states

The first screen is not a blank grid.

v1.3 promised that a new team could be productive quickly, then never described what they meet. Emptiness is a designed state: it must teach the model of the product in one screen and produce something real in one action.

Minimum event

Four answers, then work

Creating an event requires a name and a date range. Timezone is proposed from the device, discipline and vehicle are optional, and every skipped answer stays easy to add later. No wizard step may block a user who does not yet know the answer.

Every empty collection

Purpose, action, example

An empty plan, checklist, record list or form list states what it is for, offers one primary action, offers a relevant template, and shows one example entry marked clearly as an example. It never shows only column headings.

Sample event

Explorable, and removable in one action

A new account may open a fully populated sample event to learn from. It is labelled as sample everywhere it appears and can be removed in one action without touching real events.

Progressive disclosure

Earn the complexity

Field types, automation, permissions, versioning and view sharing stay available but not prominent until a team has a plan and a checklist in use. Nothing is hidden behind a setting the user cannot find when they want it.

Required rule Empty is also a runtime state, not just a first-run state: a filtered view with no matches must state the filter that produced the emptiness and offer to clear it. A user must never have to guess whether they are looking at no data or the wrong question.
11 / mobile, offline and failure states

Assume weak signal, gloves, noise and partial attention.

Offline manager

Make availability deliberate

Users choose the full event, selected days, selected views, maps and files to download. Before leaving signal, the product states what is included and what is missing.

Queued changes

Never pretend a save traveled

Each local edit visibly states saved locally / queued / synced / needs resolution. Conflicts open a comparison with an explicit choice, never a silent overwrite.

Field-friendly controls

Make core actions touchable

Mobile prioritizes Today, search, quick add, check off, capture photo, directions and plan detail. Controls meet the targets in §12, and no meaning is carried by hover alone.

Failure matrix

Every failure names a cause and a next step

A failure state must say what failed, whether the user’s data is safe, and what to do now. “Something went wrong” is not an acceptable string anywhere in the product.

11b / required failure states

The other things that go wrong.

Failure matrix
FAILUREWHAT THE USER SEES AND CAN DOWHY IT EXISTS
Content will not loadThe screen states that it could not load, whether a cached copy is being shown and how old it is, and offers retry. Cached content is labelled as cached with its time.Stale data presented as current is more dangerous than a visible error.
Permission deniedNames what was refused, who can grant it, and offers to request access. It does not silently hide the control that led there.A control that fails without explanation reads as a broken product and produces a phone call.
Record changed or archived by someone elseStates who changed it and when, shows the current value beside the user’s open copy, and lets them re-apply their edit deliberately.Two people editing the same movement during a live event is normal, not exceptional.
Stale open viewWhen underlying records change while a view is open, the view says so and offers refresh rather than reordering under the user’s hands.Content moving mid-tap causes the wrong record to be opened or completed.
Publish or sync failureThe change stays intact and marked unpublished, states why it failed and what remains queued, and offers retry. It is never discarded.Losing a typed change during a live event destroys trust in the product permanently.
Upload or photo failureKeeps the file queued locally with its target record, states the reason, and retries when possible. The form does not lose the rest of its answers.Evidence is usually captured once, in conditions that cannot be recreated.

12 / accessibility and operating environment

Requirements you can fail a build against.

v1.3 asked for readable contrast and generous targets without saying what either meant, which made them unreviewable. These thresholds are minimums, not aspirations, and apply to the shipped product on the smallest supported screen.

Binding minimums
REQUIREMENTTHRESHOLDWHY IT EXISTS
Type sizeBody text at least 15px; secondary and metadata text never below 12px; labels and status text never below 11px and never in all-caps below 12px. Text scales with the operating system setting up to 200% without loss of function.Dense 8–10px metadata was unreadable for the people this product is for, in the conditions they use it in.
ContrastAt least 4.5:1 for all text and 3:1 for icons, control borders and focus rings, in every display mode including night.Low-contrast greys disappear in sunlight and behind a scratched, wet or gloved-on screen.
Touch targetsAt least 44×44px on touch devices and 32×32px with a pointer, with at least 8px between adjacent targets. Row actions, checkboxes and overflow menus are included in this rule.Gloves and vibration make a 16px tick box a coin toss.
Keyboard operationEvery action reachable and operable by keyboard, with a visible focus indicator, logical order, Escape closing overlays and focus returning to where it was opened from.Planning happens on a laptop, at speed, and some users cannot use a pointer at all.
Assistive technologyControls have programmatic labels; dialogs are announced and trap focus; status changes such as sync, publish result and validation errors are announced, not only shown.State that is only visual excludes people and disappears the moment attention moves.
State without colorEvery status carries text or shape in addition to color, including in dense views and print.Color-only status fails for colorblind users, in sunlight, and on a photocopied sheet.
Display modesDay, night and high-contrast modes; follows the device setting; remembers an explicit choice; night mode avoids large bright surfaces.A white screen in a dark car at 22:00 destroys night vision for the person holding it and the driver beside them.
MotionRespects reduced-motion settings; no essential information conveyed only by animation; nothing that moves under the user’s finger after tap.Movement in a moving vehicle causes errors and nausea.
Latency and feedbackAny action gives feedback within 100ms. Anything longer than 1s shows progress. Locally available data opens without waiting for the network. Sync state resolves within 5s or is explicitly stated as queued.Silence after a tap is read as failure, and the tap is repeated.
One-hand reachOn phones the primary actions of a screen sit within thumb reach; destructive actions do not.The other hand is holding a tool, a radio, a door or a tire.
Feedback that must persistAnything that blocks the user, changes shared state, or needs a decision is shown in place until resolved. Transient messages are limited to confirmations of completed reversible actions, and always carry an undo.A 3-second message is the wrong container for a reason someone cannot submit.
13 / UX guardrails and delivery priorities

Power should not create a new burden.

A
Undo for the reversible; an impact statement for the rest.Reversible actions apply immediately and offer undo where they happened. Irreversible actions — merging a category, deleting a record type, removing access, permanent deletion — state which records, users and views are affected, then require explicit confirmation. Do not confirm everything; it teaches people to confirm nothing.
B
No hidden mode changes.Draft, edit, selected, filtered, offline, shared and display-mode states must be visible in the immediate workspace. Avoid controls that silently alter another user’s experience.
C
No required field unless it changes a real outcome.Required fields should be limited to identity, safety, compliance, routing or a configured workflow need. Everything else should be easy to add later.
D
No universal racing taxonomy.Provide starter templates for disciplines, but a team must be able to rename “movement,” “service,” “session,” “vehicle,” “status” and categories to match its vocabulary.
E
No control that does nothing.Every visible control either acts, explains why it cannot act, or is not shown. A control that is present but inert — a filter tab that does not filter, a count that does not open, a menu that never appears — is a defect, not an unfinished feature.
F
No claim the product cannot support.Counts, statuses, “offline ready” and “notified” must reflect verified state. If the product does not know, it says it does not know.
Build firstEvent context; quick capture; configurable collections/fields; table and list views with required responsive reflow; plan; work; linked records; offline status; source and history; first-run and empty states; the §12 minimums; undo.
Build nextSaved shared views; map, board and timeline; templates; configurable forms; publishing with §09 delivery tracking and escalation; permissions; export with supersede marking; attention queue.
Prove before expandingAutomations, formulas, deep conditional logic and cross-event reporting should follow observed team workflows, not assumed complexity.
Sequencing note §12 is not a later hardening pass. Type size, contrast, target size, keyboard operation and persistent feedback are cheap at the start and expensive to retrofit, because they change layout density everywhere.
